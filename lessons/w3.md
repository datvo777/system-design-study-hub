## Vì sao cần gateway

Không có gateway, client (web, app di động, đối tác) phải biết địa chỉ của từng service, tự xử lý xác thực với từng nơi, và gọi nhiều lần cho một màn hình. Mỗi service lại phải tự làm TLS, auth, rate limit, log. Gateway gom các việc chung đó về một chỗ.

## Các trách nhiệm điển hình

| Trách nhiệm | Ý nghĩa |
|---|---|
| Routing | `/orders/**` tới order-service, `/v2/**` tới bản mới, canary theo header |
| Xác thực | Kiểm tra JWT/OAuth2 token, API key; chuyển thông tin user xuống dưới dạng header tin cậy |
| Phân quyền thô | Scope nào được gọi API nào (phân quyền chi tiết theo dữ liệu vẫn ở service) |
| Rate limit, quota | Giới hạn theo user, API key, gói dịch vụ |
| TLS termination | Gom chứng chỉ về một chỗ |
| Aggregation | Một request từ app thành nhiều lời gọi song song xuống service, gộp kết quả |
| Biến đổi | Đổi định dạng, đổi tên trường, thêm header, nén |
| Quan sát | Access log, metric theo route, gắn trace ID |
| Cache | Cache response cho API đọc công khai |

## Backend for Frontend

Web cần nhiều dữ liệu một lần, app di động cần payload nhỏ để tiết kiệm pin và băng thông, đối tác cần API ổn định có versioning. Một gateway chung phục vụ cả ba sẽ đầy điều kiện `if (client == mobile)`. **BFF** tách thành nhiều gateway mỏng, mỗi cái do team frontend tương ứng sở hữu, được tự do thay đổi theo màn hình mà không ảnh hưởng client khác.

Cái giá: nhiều thứ phải vận hành hơn, và logic có thể bị lặp giữa các BFF. Nếu chỉ có một loại client thì không cần BFF.

## Rủi ro

- **Gateway thành monolith mới:** logic nghiệp vụ (tính giá, kiểm tra tồn kho) chui dần vào gateway. Mọi thay đổi phải deploy gateway, và gateway trở thành nút thắt của cả tổ chức.
- **Single point of failure:** gateway phải chạy nhiều instance, stateless, có autoscale; rate limit dùng chung thì counter nằm ở Redis.
- **Thêm latency:** thêm một hop mạng và xử lý; thường vài mili-giây, chấp nhận được.
- **Fan-out quá rộng:** aggregation gọi 10 service cho một request làm p99 xấu. Gọi song song, có timeout riêng, có giá trị mặc định khi một phần lỗi.

## Liên hệ với kinh nghiệm của bạn

**IBM API Connect** chính là một API gateway (DataPower Gateway thực thi chính sách, API Manager quản lý, Developer Portal cho đối tác, analytics). Bạn đã làm việc với policy assembly: `invoke`, `validate`, `rate-limit`, `oauth`, `map`. Trong phỏng vấn, mô tả đúng trách nhiệm gateway bằng chính các policy bạn đã cấu hình sẽ rất thuyết phục. Ngoài ra nên biết tên các lựa chọn khác: Kong, Spring Cloud Gateway, AWS API Gateway, Envoy.

## Nói trong phỏng vấn

> "Client đi qua API gateway: gateway terminate TLS, kiểm tra JWT, áp rate limit theo user bằng counter trong Redis, rồi route theo path. Ứng dụng di động có BFF riêng để gộp ba lời gọi của màn hình chính thành một, gọi song song với timeout 300 ms mỗi nhánh. Gateway không chứa logic nghiệp vụ."

## Lỗi hay gặp

- Đặt logic nghiệp vụ vào gateway.
- Vẽ gateway một instance.
- Tin header `X-User-Id` từ client: gateway phải xóa header do client gửi và tự đặt lại sau khi xác thực.

Khi có nhiều loại client với nhu cầu dữ liệu khác nhau rõ rệt (web, mobile, đối tác) và các team frontend cần thay đổi API theo màn hình mà không ảnh hưởng nhau. Một loại client thì không cần.

</details>

Vì service phía sau tin header đó là do gateway đặt sau khi xác thực. Nếu không xóa, client có thể tự gửi `X-User-Id` của người khác để giả mạo.

</details>

Tuần 5 sẽ thiết kế rate limiter đầy đủ; tuần này nắm cơ chế và trade-off.</div>

## 1. Token bucket

Mỗi client có một xô chứa tối đa `capacity` token, được nạp thêm `rate` token mỗi giây. Mỗi request lấy một token; hết token thì từ chối.

- **Cho phép burst** tới `capacity` rồi giữ trung bình ở `rate`. Hợp với hành vi người dùng thật (mở app thì gọi một loạt).
- Chỉ cần lưu hai giá trị: số token còn lại và thời điểm nạp lần cuối. Không cần timer: lúc có request thì tính số token được nạp thêm từ lần trước.
- Dùng rộng rãi ở API gateway (AWS API Gateway, nhiều thư viện như Bucket4j trong Java).

## 2. Leaky bucket

Request đi vào một hàng đợi có kích thước cố định và được xử lý ra với **tốc độ cố định**, như nước rò từ đáy xô. Hàng đợi đầy thì từ chối.

- Đầu ra rất đều, bảo vệ tốt hệ thống phía sau chỉ chịu được tốc độ ổn định.
- Burst bị trễ lại chứ không được xử lý nhanh; request mới có thể bị chặn sau request cũ.
- `limit_req` của Nginx hoạt động theo kiểu này.

## 3. Fixed window counter

Đếm request trong từng cửa sổ cố định (ví dụ phút 10:00–10:01). Vượt ngưỡng thì từ chối tới hết phút.

- Rất đơn giản: Redis `INCR` cộng `EXPIRE`.
- **Lỗi biên cửa sổ:** giới hạn 100/phút, client gửi 100 request lúc 10:00:59 và 100 request lúc 10:01:00, tức 200 request trong 2 giây mà vẫn hợp lệ.

## 4. Sliding window log

Lưu timestamp của từng request (ví dụ trong Redis sorted set). Với request mới: xóa các timestamp cũ hơn 60 giây, đếm phần còn lại, dưới ngưỡng thì cho qua và thêm timestamp mới.

- **Chính xác tuyệt đối** trong mọi cửa sổ 60 giây trượt.
- **Tốn bộ nhớ:** giới hạn 1.000 request/giờ nghĩa là lưu tới 1.000 timestamp cho mỗi client.

## 5. Sliding window counter

Kết hợp fixed window với nội suy: chỉ lưu counter của cửa sổ hiện tại và cửa sổ trước.

```
ước lượng = count_hiện_tại + count_trước × (phần cửa sổ trước còn nằm trong 60 giây trượt)
```

Ví dụ lúc 10:01:15, cửa sổ trước đếm được 80, cửa sổ hiện tại 30. Cửa sổ trượt 60 giây gồm 45 giây cuối của phút trước (75%): `30 + 80 × 0,75 = 90`. Giả định request phân bố đều trong phút trước, nên là xấp xỉ, nhưng trong thực tế sai số rất nhỏ (Cloudflare từng báo cáo cỡ vài phần nghìn phần trăm trên traffic thật) với chi phí chỉ hai counter.

|---|---|---|---|---|

## Những điều đi kèm

- **Trả về đúng:** HTTP `429 Too Many Requests` với `Retry-After`, và các header như `X-RateLimit-Limit`, `X-RateLimit-Remaining`.
- **Đặt ở đâu:** ở gateway cho giới hạn chung; trong service cho giới hạn nghiệp vụ (ví dụ 5 lần gửi OTP mỗi giờ).
- **Phân tán:** nhiều instance gateway phải chia sẻ counter, thường bằng Redis với Lua script để đọc, tính và ghi một cách nguyên tử.

## Liên hệ với kinh nghiệm của bạn

API Connect có policy `rate-limit` với các khái niệm rate limit và burst limit theo Plan (gói dịch vụ) của từng ứng dụng tiêu thụ. Đó chính là token bucket/fixed window được đóng gói. Khi trình bày, bạn có thể nói "trong API Connect em cấu hình burst limit 100/giây và rate limit 10.000/giờ theo plan", rồi giải thích thuật toán phía sau.

## Nói trong phỏng vấn

> "Với API công khai em dùng token bucket: capacity 20, nạp 10 token/giây cho mỗi API key, để app mở màn hình gọi một loạt vẫn qua nhưng trung bình không vượt 10/giây. Trạng thái nằm trong Redis, cập nhật bằng Lua script để nhiều instance gateway không đếm sai."

## Lỗi hay gặp

- Chỉ biết fixed window và không nhận ra lỗi biên.
- Rate limit bằng counter trong RAM của từng instance rồi nói giới hạn toàn cục.
- Quên trả `Retry-After`, client retry ngay làm tải tệ hơn.

## Năm chiến lược

| Chiến lược | Đọc | Ghi | Ưu | Nhược |
|---|---|---|---|---|
| **Cache-aside** (lazy loading) | App đọc cache; miss thì đọc DB và nạp cache | App ghi DB rồi **xóa** key cache | Đơn giản; chỉ cache dữ liệu được đọc; cache chết thì vẫn chạy (chậm hơn) | Lần đọc đầu chậm; có cửa sổ dữ liệu cũ; logic nằm trong app |
| **Read-through** | App chỉ hỏi cache; cache tự nạp từ DB khi miss | (kết hợp với chiến lược ghi khác) | Code app gọn | Cần thư viện/cache hỗ trợ loader |
| **Write-through** | | Ghi vào cache, cache ghi đồng bộ xuống DB | Cache luôn mới | Ghi chậm hơn (hai nơi); cache đầy dữ liệu có thể không bao giờ được đọc |
| **Write-back** (write-behind) | | Ghi vào cache, xác nhận ngay; đẩy xuống DB bất đồng bộ theo lô | Ghi rất nhanh, gộp được nhiều lần ghi | **Mất dữ liệu** nếu cache chết trước khi đẩy; khó đảm bảo nhất quán |
| **Write-around** | | Ghi thẳng DB, không đụng cache | Không làm bẩn cache bằng dữ liệu ít đọc | Lần đọc sau khi ghi chắc chắn miss |

## Vì sao "xóa cache" chứ không "cập nhật cache" khi ghi

Với cache-aside, sau khi ghi DB, nên **xóa** key thay vì ghi giá trị mới vào cache:

- Hai request ghi đồng thời có thể cập nhật cache theo thứ tự ngược với DB, để lại giá trị cũ vĩnh viễn trong cache.
- Giá trị trong cache thường là kết quả tổng hợp (join nhiều bảng); tính lại trong luồng ghi vừa tốn vừa dễ sai.

Xóa cũng chưa hoàn hảo: request đọc chậm có thể đọc DB giá trị cũ **trước** khi ghi, rồi ghi vào cache **sau** khi key đã bị xóa. Cách giảm: TTL ngắn làm lưới an toàn; "double delete" (xóa lần nữa sau vài trăm mili-giây); hoặc xóa cache dựa trên CDC (Debezium đọc binlog/WAL rồi xóa key) để không phụ thuộc vào code của app.

## Thứ tự: ghi DB trước hay xóa cache trước

- **Ghi DB rồi xóa cache** (khuyến nghị): nếu xóa thất bại thì dữ liệu cũ tồn tại tới hết TTL.
- **Xóa cache rồi ghi DB:** trong khoảng giữa, một request đọc có thể nạp lại giá trị cũ vào cache trước khi DB kịp ghi, và giá trị cũ ở đó tới hết TTL. Tệ hơn.

## Chọn chiến lược

- **Mặc định:** cache-aside + xóa khi ghi + TTL. Phù hợp phần lớn hệ thống đọc nhiều ghi ít.
- **Dữ liệu ghi xong đọc ngay** (profile vừa sửa): write-through, hoặc đọc từ DB cho chính người vừa ghi.
- **Ghi rất nhiều, chấp nhận mất một ít** (view count, metric): write-back, gộp lô xuống DB mỗi vài giây.
- **Dữ liệu ghi nhiều đọc ít** (log, audit): write-around.

## Liên hệ với Java

- Spring `@Cacheable` là cache-aside/read-through; `@CacheEvict` khi ghi; `@CachePut` là cập nhật cache (cẩn thận với race ở trên).
- Caffeine `LoadingCache` là read-through cho cache cục bộ, kèm `refreshAfterWrite` để làm mới nền.
- Kết hợp hai tầng hay gặp: Caffeine trong process (vài giây) trước Redis (vài phút) trước DB.

## Nói trong phỏng vấn

> "Em dùng cache-aside với Redis, TTL 10 phút. Khi cập nhật sản phẩm, service ghi DB rồi xóa key; để không phụ thuộc code ở mọi chỗ ghi, em có thêm consumer đọc CDC từ Debezium để xóa key. TTL là lưới an toàn nếu một lần xóa bị lỡ."

## Lỗi hay gặp

- Cập nhật cache thay vì xóa, rồi gặp dữ liệu cũ không bao giờ hết.
- Dùng write-back cho dữ liệu tiền bạc.
- Không có TTL, một lần xóa thất bại là dữ liệu sai mãi.

## LRU (Least Recently Used)

Giữ thứ tự theo lần truy cập gần nhất; đầy thì bỏ key ở cuối. Cài đặt kinh điển: hash map + danh sách liên kết đôi, mọi thao tác O(1). Trong Java, `LinkedHashMap` với `accessOrder = true` và ghi đè `removeEldestEntry` là một LRU cache gọn.

- **Mạnh khi:** dữ liệu vừa dùng thì sắp dùng lại (tính cục bộ theo thời gian): session, trang vừa xem.

## LFU (Least Frequently Used)

## Trong thực tế không ai dùng bản "thuần"

- **Redis** dùng LRU và LFU **xấp xỉ**: lấy mẫu vài key ngẫu nhiên (`maxmemory-samples`, mặc định 5) rồi bỏ key tệ nhất trong mẫu, để không phải duy trì cấu trúc dữ liệu đắt cho hàng triệu key. LFU của Redis dùng bộ đếm logarit 8 bit có giảm dần theo thời gian (`lfu-decay-time`).
- Các chính sách của Redis: `allkeys-lru`, `allkeys-lfu`, `volatile-lru`, `volatile-lfu`, `volatile-ttl`, `allkeys-random`, `noeviction` (mặc định: hết bộ nhớ thì báo lỗi khi ghi). Với Redis dùng làm cache, nên chọn `allkeys-lru` hoặc `allkeys-lfu`. Với Redis giữ dữ liệu không được mất (lock, queue), dùng `noeviction` và theo dõi bộ nhớ.
- **Caffeine** (Java) dùng **W-TinyLFU**: một cửa sổ LRU nhỏ cho key mới, vùng chính được bảo vệ bằng tần suất, và một "count-min sketch" ước lượng tần suất bằng rất ít bộ nhớ. Key mới chỉ được nhận vào vùng chính nếu tần suất của nó cao hơn key sắp bị bỏ. Cách này chống được cả quét một lần lẫn xu hướng thay đổi, với tỷ lệ hit gần tối ưu.

| Mẫu truy cập | Chọn |

| Truy cập gần đây dự báo tốt (session, feed mới) | LRU |

| Cache cục bộ trong Java | Caffeine (W-TinyLFU), không cần tự chọn |
| Không chắc | `allkeys-lfu` trên Redis thường tốt hơn LRU với traffic web có key nóng |

> "Redis cache em đặt `allkeys-lfu` vì traffic sản phẩm có tập key rất nóng và có job đồng bộ quét toàn bộ danh mục mỗi đêm; với LRU, job đó sẽ đẩy key nóng ra. Cache cục bộ em dùng Caffeine, vốn dùng W-TinyLFU."

## Lỗi hay gặp

- Để Redis cache ở `noeviction` mặc định: đầy bộ nhớ thì mọi lệnh ghi lỗi.
- Dùng `volatile-*` nhưng quên đặt TTL cho key, nên Redis không có gì để bỏ.

## Cache stampede (thundering herd, dogpile)

Trang chủ đọc key `homepage:banners` 5.000 lần/giây. Key hết hạn; trong khoảng 50 ms trước khi ai đó nạp lại, hàng trăm tới hàng nghìn request cùng miss và cùng chạy một query nặng. DB quá tải, query chậm thêm, cửa sổ miss kéo dài, càng nhiều request dồn xuống.

**Cách chặn:**

1. **Chỉ một request được nạp (mutex/single-flight):** request miss thử `SET lock:key 1 NX EX 5`; ai lấy được lock thì đọc DB và nạp cache; người khác chờ ngắn rồi đọc lại cache, hoặc trả giá trị cũ. Trong một process, Caffeine `LoadingCache` đã tự gộp các lần nạp cùng key.
2. **Làm mới sớm:** nạp lại trước khi hết hạn. Đơn giản nhất là lưu kèm "thời điểm nên làm mới" sớm hơn TTL thật; request nào thấy đã quá thời điểm đó thì làm mới ở nền. Bản xác suất (XFetch) cho mỗi request một xác suất nhỏ tự làm mới, tăng dần khi gần hết hạn, để không cần lock.
3. **Phục vụ dữ liệu cũ trong lúc làm mới (stale-while-revalidate):** không bao giờ để key "biến mất"; trả giá trị cũ ngay, làm mới bất đồng bộ.
4. **Key cực nóng không hết hạn:** job nền cập nhật định kỳ.

## Cache penetration

Kẻ xấu (hoặc lỗi client) hỏi `product:999999999`, sản phẩm không tồn tại. Cache không có, DB cũng không có, nên không có gì để cache, và mọi request đều xuống DB.

**Cách chặn:**

1. **Cache cả kết quả rỗng** với TTL ngắn (30–60 giây): `product:999999999 = NULL`.
2. **Bloom filter** chứa toàn bộ ID hợp lệ: nói "chắc chắn không có" thì trả 404 ngay. Bloom filter có thể báo nhầm "có" (false positive) nhưng không bao giờ báo nhầm "không"; vài trăm MB đủ cho hàng tỷ ID với tỷ lệ nhầm khoảng 1%.
3. **Validate đầu vào:** ID sai định dạng thì từ chối ở gateway.
4. **Rate limit** theo client gửi nhiều request 404.

## Cache avalanche

Hai kịch bản:

- **Nhiều key hết hạn cùng lúc:** nạp sẵn 1 triệu sản phẩm lúc 2 giờ sáng với TTL 1 giờ, 3 giờ sáng tất cả cùng hết hạn.
- **Cụm cache chết** hoặc restart: tỷ lệ hit về 0.

**Cách chặn:**

1. **TTL có jitter:** `TTL = 3600 + random(0, 600)` để thời điểm hết hạn rải đều.
2. **Cache có HA:** Redis có replica và failover (Sentinel hoặc Cluster); trải qua nhiều AZ.
3. **Nhiều tầng:** cache cục bộ (Caffeine) đỡ một phần khi Redis có vấn đề.
4. **Bảo vệ database:** circuit breaker, giới hạn số kết nối đồng thời xuống DB, rate limit, trả lỗi có kiểm soát hoặc dữ liệu mặc định thay vì để DB sập.
5. **Warm-up** trước khi đưa cache mới vào phục vụ.

## Nói trong phỏng vấn

> "Key trang chủ em không để hết hạn kiểu cứng: lưu kèm thời điểm làm mới mềm, quá thời điểm đó thì một request lấy lock `SET NX` để nạp lại ở nền, các request khác vẫn nhận bản cũ. Với tra cứu sản phẩm, ID không tồn tại được cache rỗng 60 giây và có Bloom filter ở phía trước. Mọi TTL đều cộng thêm jitter 10% để tránh hết hạn đồng loạt."

## Lỗi hay gặp

- Nhầm ba khái niệm với nhau.
- Lock khi nạp nhưng không có thời hạn cho lock: request giữ lock chết là không ai nạp được nữa.
- Cache rỗng với TTL dài: sản phẩm vừa được tạo vẫn báo không tồn tại lâu.

## Vì sao sharding không cứu được

Redis Cluster chia key theo hash slot: `CRC16(key) mod 16384`. Một key luôn nằm ở đúng một slot, tức đúng một node primary. Một node Redis xử lý lệnh trên một luồng chính, thường khoảng 100 nghìn tới vài trăm nghìn thao tác đơn giản mỗi giây tùy phần cứng và kích thước value. Flash sale với 1 triệu request/giây cùng đọc `product:iphone17` thì node đó quá tải dù cluster có 100 node; 99 node còn lại gần như rảnh. Băng thông mạng của node cũng là giới hạn: value 10 KB × 1 triệu lần/giây là 10 GB/giây.

- Mỗi app instance giữ bản sao của key nóng trong RAM (Caffeine) với TTL rất ngắn, 1–2 giây.
- Tải xuống Redis ≈ số instance × (1 / TTL) cho mỗi key, không phụ thuộc vào lượng request của người dùng.
- Dùng `refreshAfterWrite` hoặc single-flight để mỗi instance chỉ có một lần nạp đồng thời.
- **Đánh đổi:** dữ liệu có thể cũ tới TTL; các instance có thể lệch nhau trong khoảng đó. Với thông tin sản phẩm hiển thị thì ổn; với **tồn kho dùng để quyết định bán** thì không được dựa vào bản cache này (bước trừ kho cuối cùng phải làm trên nguồn nhất quán, tuần 13).
- Redis 6+ có **client-side caching** (lệnh `CLIENT TRACKING`): Redis ghi nhớ client đã đọc key nào và gửi thông báo invalidate khi key đổi, giúp cache cục bộ cũ ít hơn. Cần thư viện client hỗ trợ.

## Cách 2: nhân bản key trên nhiều shard

- Ghi giá trị vào N bản: `product:iphone17:1`, `product:iphone17:2`, … `:N`. Đặt tên sao cho các bản rơi vào các slot khác nhau.
- Khi đọc, chọn ngẫu nhiên một hậu tố trong 1..N. Tải chia đều cho tối đa N shard.
- Khi ghi, phải cập nhật cả N bản (hoặc xóa cả N bản). Giữa các lần cập nhật, các bản có thể lệch nhau trong chốc lát.
- Hợp khi không muốn đổi code ở tất cả service để thêm cache cục bộ, hoặc khi giá trị lớn và nhiều service khác nhau cùng đọc.

## Các cách khác

- **Đọc từ replica:** Redis replica phục vụ đọc (`READONLY` trong cluster). Nhân thêm năng lực đọc cho shard đó, dữ liệu có thể trễ một chút.
- **CDN hoặc cache ở edge:** nếu dữ liệu công khai (trang sản phẩm), cache response ở CDN vài giây; phần lớn request không tới hệ thống của bạn.
- **Phát hiện hot key:** `redis-cli --hotkeys` (cần chính sách LFU), thống kê ở proxy, hoặc metric phía client. Hệ thống lớn tự phát hiện key nóng và tự bật cache cục bộ cho key đó.

## Phân biệt với write hot key

Đọc nóng giải quyết bằng **sao chép** (nhiều bản để đọc). Ghi nóng (một counter bị tăng 100 nghìn lần/giây) không sao chép được vì các bản sẽ lệch nhau; phải **chia nhỏ rồi gộp** (sharded counter, tuần 11) hoặc gom lô.

## Nói trong phỏng vấn

> "Trang sản phẩm flash sale có một key bị đọc khoảng 1 triệu lần/giây, vượt khả năng một shard Redis. Em thêm cache Caffeine TTL 1 giây trong mỗi instance, nên Redis chỉ nhận khoảng số instance lần đọc mỗi giây. Thông tin hiển thị cũ 1 giây là chấp nhận được; còn số tồn kho khi đặt hàng vẫn được trừ nguyên tử ở Redis/DB, không đọc từ cache cục bộ."

## Lỗi hay gặp

- Đề xuất "thêm node Redis" cho một key nóng.
- Dùng cache cục bộ cho dữ liệu cần quyết định chính xác (tồn kho, số dư).
- Nhân bản key mà quên cập nhật hoặc xóa đủ N bản.

## Vì sao Redis làm được nhiều việc hơn cache

Nhờ cấu trúc dữ liệu và thao tác nguyên tử, Redis thường được dùng cho:

- **Rate limiter:** `INCR` + `EXPIRE`, hoặc Lua script cho token bucket.
- **Distributed lock** đơn giản: `SET key value NX PX 30000` (cẩn thận với giới hạn của nó, tuần 12).
- **Leaderboard:** sorted set, `ZINCRBY` và `ZREVRANGE` lấy top N trong O(log N).
- **Session store, giỏ hàng:** hash với TTL.
- **Đếm unique** xấp xỉ: HyperLogLog, khoảng 12 KB cho hàng tỷ phần tử với sai số khoảng 0,81%.
- **Hàng đợi nhẹ:** list hoặc stream với consumer group.
- **Geo:** tìm tài xế gần nhất (`GEOSEARCH`), dùng trong bài Uber.

## Những điểm cần cẩn thận với Redis

- **Một luồng chính:** một lệnh chậm chặn mọi lệnh khác. Tránh `KEYS *` (dùng `SCAN`), tránh value cực lớn và `HGETALL`/`SMEMBERS` trên tập hàng triệu phần tử (big key).
- **Lưu bền không giống database:** AOF với `appendfsync everysec` có thể mất khoảng 1 giây dữ liệu khi sập; replication bất đồng bộ nên failover có thể mất các lần ghi chưa kịp sang replica. Đừng dùng Redis làm nguồn sự thật cho dữ liệu tiền bạc.
- **Cluster và multi-key:** lệnh nhiều key (`MGET`, transaction, Lua) chỉ chạy được khi các key cùng slot; dùng **hash tag** `{user:42}:cart`, `{user:42}:profile` để ép cùng slot.
- **Giấy phép:** từ 2024 Redis đổi giấy phép (sau đó thêm AGPL ở bản 8); cộng đồng có bản fork mã nguồn mở **Valkey**, được nhiều cloud cung cấp. Biết điều này giúp bạn trả lời nếu được hỏi về lựa chọn công nghệ.

**Queue (point-to-point):** dùng khi có **một việc cần làm đúng một lần**: gửi email, resize ảnh, xử lý đơn. Nhiều consumer cùng đọc một queue là mẫu **competing consumers**, giúp scale ngang phần xử lý. Message thường bị xóa sau khi được xác nhận.

**Topic (pub/sub):** dùng khi có **một sự kiện mà nhiều bên quan tâm**: "đơn hàng đã tạo" thì dịch vụ email, kho, analytics, gợi ý đều cần biết. Producer không cần biết ai đang nghe; thêm một bên nghe mới không phải sửa producer.

## Kafka: log có consumer group

Kafka không có "queue" theo nghĩa cũ. Topic là một **log chỉ ghi thêm**, chia thành partition; message được giữ theo thời gian retention (ví dụ 7 ngày) bất kể đã được đọc hay chưa. Mỗi consumer group tự giữ offset của mình.

- Trong một group, mỗi partition chỉ được một consumer đọc → hành xử như queue, chia việc theo partition. **Số consumer hữu ích tối đa bằng số partition.**
- Các group khác nhau đọc độc lập → hành xử như topic.
- Vì message không bị xóa khi đọc, có thể **replay**: tạo group mới đọc lại từ đầu, hoặc lùi offset để xử lý lại sau khi sửa bug.

## Vì sao thứ tự dễ bị phá

Ngay cả khi broker giữ đúng thứ tự, thứ tự xử lý vẫn có thể sai vì:

- **Nhiều consumer song song:** consumer A nhận `OrderCreated`, consumer B nhận `OrderCancelled` của cùng đơn; B xử lý xong trước.

## Những chi tiết hay làm vỡ thứ tự

1. **Producer retry:** bật `enable.idempotence=true` (mặc định từ Kafka 3.0). Broker dùng sequence number để loại bản trùng và giữ thứ tự, kể cả khi có tới 5 request đang bay (`max.in.flight.requests.per.connection ≤ 5`).
2. **Thay đổi số partition:** `hash(key) mod N` đổi khi N đổi, nên cùng key có thể sang partition mới trong khi message cũ còn ở partition cũ. Tạo đủ partition ngay từ đầu, hoặc chuyển đổi có kế hoạch.
3. **Consumer xử lý song song bên trong:** đọc tuần tự rồi đẩy vào thread pool là mất thứ tự. Nếu cần song song trong consumer, chia lại theo key (mỗi key một hàng đợi nội bộ), như thư viện Confluent Parallel Consumer làm.
4. **Retry làm đảo thứ tự:** đẩy message lỗi sang retry topic để xử lý sau thì message sau của cùng key có thể chạy trước. Với dữ liệu cần thứ tự nghiêm, phải chặn cả key đó cho tới khi message lỗi được xử lý, hoặc dùng version để bỏ qua sự kiện cũ.
5. **Hot key:** một thực thể quá nhiều sự kiện dồn hết vào một partition, partition đó trễ.

## Thiết kế để không phụ thuộc thứ tự

Cách bền vững nhất là làm consumer chịu được message đến sai thứ tự:

- **Version hoặc sequence trong sự kiện:** chỉ áp dụng nếu `event.version > current.version`, bỏ qua sự kiện cũ.
- **Sự kiện mang trạng thái đầy đủ** (state transfer) thay vì chỉ phần thay đổi: sự kiện mới nhất luôn thắng.
- **State machine** từ chối chuyển trạng thái không hợp lệ (đơn đã hủy không thể sang "đã giao").

## Liên hệ với IBM MQ

Một queue MQ là FIFO trong cùng mức priority, nhưng khi có nhiều consumer đọc song song thì thứ tự xử lý không còn đảm bảo. MQ có **message grouping** (GroupId, đọc theo logical order) để giữ một nhóm message đi cùng nhau, và cách phổ biến là một consumer duy nhất cho queue cần thứ tự nghiêm. Kafka giải bài toán này mềm dẻo hơn nhờ partition key.

## Exactly-once thật sự có ở đâu

1. **Bên trong Kafka:** idempotent producer + transaction cho phép "đọc từ topic A, xử lý, ghi ra topic B, commit offset" nguyên tử (consumer đọc với `isolation.level=read_committed`). Kafka Streams bật bằng `processing.guarantee=exactly_once_v2`. Đảm bảo này chỉ áp dụng khi cả đầu vào lẫn đầu ra đều là Kafka.
2. **Message broker và database cùng một giao dịch phân tán (XA/2PC):** đây là cách IBM MQ truyền thống làm với syncpoint và XA: lấy message ra khỏi queue và ghi database trong cùng một global transaction do transaction manager điều phối. Đúng, nhưng chậm, phức tạp, và kém phổ biến trong kiến trúc cloud-native.
3. **Ghi offset cùng giao dịch với dữ liệu:** consumer lưu offset đã xử lý vào cùng database, trong cùng transaction với dữ liệu nghiệp vụ; khi khởi động thì đọc offset từ DB chứ không từ Kafka.

## Effectively once: cách làm phổ biến

Với hệ thống nói chuyện với bên ngoài (gửi email, gọi cổng thanh toán, ghi DB khác), cách thực tế là:

> **at-least-once delivery + idempotent processing = effectively-once**

Consumer nhận trùng thì nhận ra và bỏ qua (bài tiếp theo). Đây là câu trả lời interviewer muốn nghe.

## Phía producer cũng có câu chuyện riêng

- Producer gửi rồi không nhận được ack (timeout): gửi lại có thể tạo bản trùng trên broker. Kafka idempotent producer loại được trùng do retry trong một phiên producer.
- Ghi DB rồi publish sự kiện là hai thao tác tách rời: sập ở giữa thì DB có dữ liệu mà sự kiện không bao giờ được gửi, hoặc ngược lại. Lời giải là **transactional outbox** (tuần 10): ghi sự kiện vào bảng outbox cùng transaction với dữ liệu, một tiến trình khác đọc outbox và publish.

## Nói trong phỏng vấn

> "Em dùng at-least-once: consumer xử lý xong mới commit offset, producer bật idempotence và retry. Vì message có thể trùng, mọi consumer đều idempotent dựa trên event ID. Exactly-once của Kafka em chỉ dùng cho pipeline Kafka sang Kafka bằng Kafka Streams."

## Lỗi hay gặp

- Nói "Kafka có exactly-once nên không lo trùng" khi consumer ghi vào database hoặc gọi API bên ngoài.
- Bật auto-commit trong Kafka consumer rồi xử lý bất đồng bộ: offset được commit trước khi xử lý xong, thành at-most-once ngoài ý muốn.

- Dùng offset hoặc ID do broker sinh làm khóa chống trùng.

## Tự kiểm tra

<details>
<summary>Thiết kế consumer idempotent với at-least-once ra sao?</summary>

Mỗi sự kiện có event ID cố định từ producer. Consumer, trong cùng một DB transaction, insert event ID vào bảng có khóa chính và thực hiện thay đổi nghiệp vụ; trùng thì rollback và ack. Hoặc dùng ràng buộc duy nhất nghiệp vụ, hoặc update có điều kiện theo trạng thái/version. Gọi bên ngoài thì kèm idempotency key.

</details>

<details>
<summary>Vì sao "SELECT xem đã xử lý chưa, nếu chưa thì xử lý" không an toàn?</summary>

Hai consumer (hoặc hai lần giao lại chồng nhau) cùng SELECT thấy "chưa" và cùng xử lý. Phải dựa vào ràng buộc duy nhất của database để chỉ một bên thắng.

</details>

<details>
<summary>Vì sao không nên dùng Kafka offset làm khóa chống trùng?</summary>

Vì cùng một sự kiện nghiệp vụ có thể được publish nhiều lần (producer retry, outbox gửi lại) với offset khác nhau. Khóa phải là ID do producer gán cho sự kiện.

</details>

<div class="tldr">Dead letter queue (DLQ) là nơi chứa message không xử lý được sau một số lần thử, để chúng không chặn các message khác và không bị mất. DLQ chỉ có giá trị khi có cảnh báo, có đủ thông tin để điều tra, và có công cụ để xử lý lại.</div>

## Vì sao cần

Một **poison message** (sai định dạng, tham chiếu dữ liệu không tồn tại, gây lỗi do bug) sẽ lỗi ở mọi lần thử. Nếu consumer cứ retry mãi:

- Với queue/partition có thứ tự, mọi message phía sau bị chặn.
- Consumer tốn tài nguyên vô ích, log đầy lỗi lặp lại.

Nếu bỏ qua thì mất dữ liệu. DLQ là con đường thứ ba: **cách ly** message lỗi, giữ lại để xử lý sau.

1. **Phân loại lỗi:**
   - **Tạm thời** (timeout, DB tạm quá tải, 503): retry có backoff.
   - **Vĩnh viễn** (JSON sai, validation lỗi, không tìm thấy dữ liệu bắt buộc): retry vô ích, đưa thẳng vào DLQ.
2. **Retry có độ trễ:** retry ngay lập tức trong consumer thường vô ích với lỗi do dependency. Dùng retry topic có độ trễ (30 giây, 5 phút, 1 giờ) để không chặn partition chính.
3. **Hết số lần thử** thì chuyển sang DLQ, ack message gốc.
4. **Cảnh báo** khi DLQ có message mới hoặc vượt ngưỡng.
5. **Điều tra, sửa, replay:** sửa bug hoặc dữ liệu, rồi đưa message từ DLQ trở lại topic chính.

## Message trong DLQ cần mang theo gì

- Nội dung gốc, không sửa.
- Topic/queue nguồn, partition, offset.
- Thông tin lỗi: loại exception, message, stack trace rút gọn.
- Số lần đã thử, thời điểm lần đầu và lần cuối.
- Correlation ID / trace ID để tìm log liên quan.

## Cách các hệ thống hỗ trợ

| Hệ thống | Cơ chế |
|---|---|
| IBM MQ | Backout: `BOTHRESH` (ngưỡng) và `BOQNAME` (backout queue) trên queue; message có `BackoutCount` tăng mỗi lần rollback. Ngoài ra queue manager có dead-letter queue (`DEADQ`) cho message không giao được (queue đích không tồn tại, đầy), kèm header DLH ghi lý do |
| Kafka | Không có DLQ sẵn ở broker; xử lý ở phía consumer. Spring Kafka: `DefaultErrorHandler` + `DeadLetterPublishingRecoverer`, hoặc `@RetryableTopic` tạo retry topic và DLT tự động |
| RabbitMQ | Dead letter exchange (`x-dead-letter-exchange`) khi message bị reject, hết TTL, hoặc queue đầy |
| AWS SQS | Redrive policy với `maxReceiveCount` |

Bạn đã làm việc với backout queue của MQ và App Connect (catch/failure terminal, backout handling). Đây là kinh nghiệm thật đáng kể lại.

## Cẩn thận với thứ tự

Đẩy một message vào retry/DLQ rồi xử lý tiếp message sau nghĩa là chấp nhận **mất thứ tự** cho key đó. Nếu thứ tự là bắt buộc (sự kiện của cùng tài khoản), có thể phải tạm dừng cả key đó, hoặc dựa vào version để sự kiện cũ được replay sau bị bỏ qua đúng cách.

## Nói trong phỏng vấn

> "Consumer phân biệt lỗi tạm thời và vĩnh viễn. Lỗi tạm thời đi qua retry topic 30 giây rồi 5 phút; lỗi vĩnh viễn hoặc hết lượt thử thì vào DLT kèm header lỗi và trace ID. Có cảnh báo khi DLT có message mới, và một công cụ nội bộ để xem, sửa và replay về topic chính."

## Lỗi hay gặp

- Có DLQ nhưng không ai theo dõi, message nằm đó hàng tháng.
- Retry vô hạn trong consumer, một message chặn cả partition.
- Đưa vào DLQ mà không lưu nguyên nhân lỗi.

## Tự kiểm tra

<details>
<summary>Poison message là gì và vì sao nguy hiểm khi không có DLQ?</summary>

Message luôn gây lỗi mỗi lần xử lý. Không có DLQ thì consumer retry mãi, chặn các message phía sau trong cùng queue/partition và tốn tài nguyên; bỏ qua thì mất dữ liệu.

</details>

<details>
<summary>Vì sao không nên retry ngay lập tức nhiều lần trong consumer?</summary>

Lỗi tạm thời thường do dependency cần thời gian phục hồi; retry dồn dập vô ích và còn thêm tải. Đồng thời chặn partition. Retry với độ trễ tăng dần qua retry topic hiệu quả hơn.

</details>

<details>
<summary>Trong IBM MQ, backout queue khác dead-letter queue của queue manager thế nào?</summary>

Backout queue (BOQNAME) nhận message mà ứng dụng xử lý thất bại và rollback vượt ngưỡng BOTHRESH; việc chuyển do ứng dụng/framework đảm nhận. Dead-letter queue của queue manager (DEADQ) nhận message không thể giao tới đích (queue không tồn tại, đầy, bị cấm), do chính MQ đặt vào kèm header DLH ghi lý do.

</details>
